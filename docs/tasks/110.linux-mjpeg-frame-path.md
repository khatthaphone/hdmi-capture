# 110 — MJPEG decode (libjpeg-turbo) and the live frame path to the renderer

**Status:** in-progress
**Phase:** Phase 10: Linux
**Depends on:** 107, 108
**Complexity:** complex — suggested model: Claude Code → sonnet · Codex → terra

## Objective

Get a live picture: V4L2 buffers (MJPEG via libjpeg-turbo, or YUYV/NV12 directly) go to the shared renderer with no per-frame allocation. Benchmark decode against the Windows numbers.

## Relevant files / modules

- `docs/spec.md` §14 — Linux requirements
- `docs/research/linux.md` — research (2026-10-23)
- `Apps/Windows/src/HDMICaptain.Media` MJPEG decoder and task 090 — decode into reused planes, drop the first non-JPEG frames
- `docs/research/windows.md` §2 measured decode times on this PC
- `native/render-gles/` planar YUV input (Android 074)

## Steps

1. Share the libjpeg-turbo P/Invoke wrapper with Windows if it can move to a `net10.0` project without Windows references. Otherwise port it, and log which.
2. Decode on the capture thread into reused planar buffers (4:2:2/4:2:0 from the JPEG header). Skip corrupt and non-JPEG frames (count them).
3. YUYV and NV12 go straight from the mmap buffer to the renderer upload; requeue the buffer as soon as the upload is done.
4. Benchmark `--bench-mjpeg N` on saved frames (in WSL and on real Linux later) and compare with the Windows table in `windows.md`.
5. Stats HUD numbers (fps, drops, decode ms) come from the same counters.

## Acceptance criteria

- [ ] Live 1080p60 picture from the UGREEN-25854 in the app window (in WSL if 108 said go, otherwise on real Linux)
- [ ] Decode benchmark logged next to the Windows numbers
- [ ] No managed allocation per frame in steady state (checked with `dotnet-counters` gen0 rate or an allocation test)
